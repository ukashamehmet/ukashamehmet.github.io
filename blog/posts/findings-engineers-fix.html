Security craft / Reporting

Write findings engineers can actually fix

A penetration test does not reduce risk by producing a document. It reduces risk when someone with commit access understands the finding, agrees on the fix, and ships it. The report exists to make that happen.

Okasha Mehmood 6 min read Sanitized · no client identifiers

I have read a lot of security reports. The weak ones share a shape: a dramatic title, a screenshot, a CVSS score, and a recommendation to “validate input” or “implement proper security.” The finding may be real, but the engineer receiving it has to reverse-engineer the report before they can write a patch.

A useful finding answers five questions quickly: what is wrong, where, why it matters, what exactly to change, and how we will know it is fixed. Everything else is supporting material.

1. Make the title a fact, not a mood

“Critical API vulnerability” is not a title. It tells the reader nothing they can route to a team. A better title names the object and the failure:

Cross-tenant read access on the case-detail endpoint due to missing organization scope

The title should survive being pasted into a ticket with no other context. If it needs the executive summary to make sense, it is not finished.

2. Put impact before methodology

Engineers are busy. Executives are busier. Start with the sentence that explains the consequence: “An authenticated user from one organization can read another organization’s case records by changing the object identifier.” Then add the conditions: authentication required, role required, data exposed, actions possible.

Methodology belongs after impact. The reader should know whether they need to keep reading before they encounter the request dump.

3. Give the smallest reproducible proof

A finding should include the minimum sequence that demonstrates the issue: the request, the relevant state, and the observed result. Remove unrelated headers, tokens, cookies, and client data. Use placeholders consistently. 

# Minimal proof — values sanitized
1. Sign in as Tenant A.
2. Request /api/<resource>/<tenant-b-object>.
3. Observe HTTP 200 with Tenant B's record.

Expected: 403 or 404.

Do not paste a 400-line proxy history. Link to a redacted evidence file if more detail is needed. The report should be readable; the appendix can be exhaustive.

4. Separate the symptom from the root cause

“The endpoint returns another tenant’s record” is the symptom. The root cause might be a global queryset, a missing object permission, a serializer that fetches related objects without scoping, or a background job that bypasses the request layer.

If the root cause is not confirmed, say so. “The likely cause is a global lookup; the exact call path should be confirmed during remediation” is more honest than inventing certainty. Engineers will trust the report more when it distinguishes observation from inference.

Useful distinction

Observation: what the response showed. Inference: why the code probably behaves that way. Recommendation: what to change. Do not blur the three.

5. Recommend a change, not a virtue

“Sanitize input” is not actionable. “Replace the extension blocklist with a canonicalized allowlist, verify magic bytes, and store uploads outside the web root” is. The recommendation should identify the control, the location, and the acceptance criterion.

  • Control: what mechanism should exist.
  • Location: which component or layer should own it.
  • Acceptance: what a retest will observe when it is correct.

Where possible, include a short code sketch. Keep it illustrative, not a full patch. The engineering team owns the implementation; the report owns the security requirement.

6. Make severity explain itself

CVSS is useful for consistency, not for communication. A score without a rationale is noise. Explain the inputs: what access is needed, what data or capability is reached, what user interaction is required, and what compensating controls exist.

If a finding is high impact but difficult to exploit, say both. If it is easy but limited, say that too. The goal is a defensible priority, not a dramatic number.

7. Close the loop with a retest

The report should define what fixed means before the fix is written. That turns the retest into a verification step rather than a negotiation. For the tenant example, fixed means: the original request returns 403/404, the collection endpoint returns only own-tenant rows, the write path rejects the foreign object, and the regression test runs in CI.

A closure memo is short: what was tested, what changed, what passed, what remains. It gives the client evidence for auditors and gives the engineering team a clean end state.

A compact finding template

Title: [Object] + [failure] + [condition]
Impact: one sentence, business language
Affected: component, endpoint, role, environment
Evidence: minimal reproducible sequence
Root cause: confirmed / likely, with code reference
Fix: control + location + acceptance criteria
Severity: rating + rationale
Retest: exact checks that must pass
References: standards, CWE, related findings

This is not a template problem. It is a respect problem. The report is written for the person who has to change the system, not for the person who wants to look thorough. The best finding is the one that gets fixed quietly, correctly, and without a follow-up meeting to explain what it meant.
