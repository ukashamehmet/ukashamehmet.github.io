Application security / Authorization

The tenant boundary is a query, not a checkbox

Multi-tenant authorization fails in the same place again and again: the code knows who the user is, but not which rows that user is allowed to touch. The durable fix is not a controller check. It is a data-layer constraint.

Okasha Mehmood 9 min read Sanitized · no client identifiers

A multi-tenant application can pass every authentication test and still leak every customer’s data. The login is correct. The session is valid. The role check runs. The bug is one layer lower: the object being requested is fetched by an identifier the user controls, from a dataset that is not scoped to their tenant.

This is usually described as BOLA — broken object-level authorization — or IDOR. The labels are useful, but they can make the problem sound like a missing if statement. It is more useful to think of it as a missing invariant: every object access must be evaluated inside a tenant scope.

Authentication answers the wrong question

Authentication asks: who is this? The tenant boundary asks a second question: is this row inside the caller’s tenant? A request can satisfy the first and fail the second. When an endpoint fetches a record globally and only checks that the caller is logged in, the identifier in the URL becomes an authorization decision made by the client.

If the database query does not know about the tenant, the controller is already too late.

The failure pattern, in four shapes

The same root cause appears in predictable places. When I test a multi-tenant product, I look for all four:

  • Direct object access. A detail endpoint fetches by a public or sequential identifier and checks only is_authenticated.
  • Collection leakage. A list, search, dashboard, or export endpoint queries a global table and filters in the serializer or template.
  • Nested objects. A case is scoped correctly, but its comments, files, staff members, or audit entries are fetched through a separate unscoped query.
  • Write-path gaps. Reads are scoped, but a PATCH, assignment, comment, or bulk action resolves the object through a different code path.

The dangerous ones are rarely the obvious “get user by id” route. They are the background job, the CSV export, the notification preview, the GraphQL node resolver, and the admin convenience endpoint that was added after the authorization review.

A test matrix that finds the gap

A two-tenant test pair is the most efficient tool I know for this class of bug. Create Tenant A and Tenant B, each with a user at the same role, and one object in each tenant. Then test every action as A against B’s object. Repeat with different roles, because the bug may exist only for a lower-privileged user.

Then extend the matrix to the less obvious surfaces: search, pagination, bulk update, file download, comment threads, audit logs, notifications, GraphQL nodes, and any endpoint that accepts an array of identifiers. A single missed route is enough.

Why controller checks drift

A typical first fix looks like this: fetch the object, compare its organization to the current user, and return an error if they differ. It works for the route where the bug was found. It does not create an invariant. New routes, new serializers, new background jobs, and refactors can bypass the check without anyone noticing.

The better pattern is to make the scoped queryset the only way to reach the model in request-handling code, then enforce ownership at retrieval time. The code should look boring: 

# The tenant comes from the authenticated session, never from a header or body.
class CaseQuerySet(models.QuerySet):
    def for_tenant(self, tenant):
        return self.filter(organization=tenant)


def get_case(request, public_id):
    return get_object_or_404(
        Case.objects.for_tenant(request.tenant),
        public_id=public_id,
    )

This does two things at once. It makes the common path safe by default, and it makes the unsafe path visible in review: a query without for_tenant() is now an exception that needs a reason.

Design rule

Never derive the tenant from client-controlled input. Take it from the authenticated session or a trusted server-side mapping. A tenant header is an assertion, not an identity.

Make the fix testable

A boundary that is not tested will drift. Add a small regression suite that creates two tenants, signs in as each, and asserts that cross-tenant reads, writes, exports, and nested-object access fail. Run it in CI on every route that accepts an object identifier. 

def test_cannot_read_other_tenant_case(client, tenant_a, tenant_b):
    case_b = make_case(tenant=tenant_b)
    client.force_login(tenant_a.user)

    response = client.get(f"/api/cases/{case_b.public_id}/")

    assert response.status_code in (403, 404)

The assertion should be 403 or 404, not a check on the response body. A serializer that hides a field after the query has already loaded the row is not a tenant boundary; it is a presentation choice.

What good looks like in review

  • Every object query has an explicit tenant scope, and the scope comes from the session.
  • Foreign objects fail closed with 404, not a partial response.
  • Nested resources are scoped through their parent, not through a global lookup.
  • Exports, search, notifications, and background jobs use the same authorization primitive.
  • Two-tenant regression tests run in CI, not as a manual pre-release checklist.
  • Production debug behavior is off, so an exception cannot disclose the query that failed.

None of this is exotic. It is the unglamorous work of putting the boundary where the data is read, instead of hoping every new endpoint remembers a rule. That is the difference between a check and an invariant — and between a test that passes and a tenant boundary that holds.
