Mobile reversing / Android

What a rogue VPN service looks like from the inside

A malicious app does not need root to become the device’s network path. It only needs the user to tap “allow” on a VPN consent prompt. Here is what happens next — and what the app can, and cannot, see.

Okasha Mehmood 8 min read Sanitized · no live indicators

Android’s VpnService is a legitimate API. It lets a user choose an application to route device traffic through a virtual network interface — the basis of corporate VPNs, privacy tools, and traffic analyzers. The permission prompt is the security boundary: the user is handing an app a position of significant control.

In the sample I analysed, the app presented itself as a municipal traffic-notice utility. It did not ask for root. It did not need an exploit. It asked for VPN access, and that was enough to become the device’s egress point.

The manifest is the first signal

Static review starts with capabilities. The interesting permissions were not unusual on their own; the combination was.

  • BIND_VPN_SERVICE — the app can implement a VPN service and receive the user’s consent.
  • RECEIVE_BOOT_COMPLETED — the service can be restarted after a reboot.
  • REQUEST_INSTALL_PACKAGES — the app can prompt the user to install another APK.

A single one of these may be legitimate. Together, they describe an app that can persist, control the network path, and bring in a second stage. That is a dropper pattern, not a traffic-notice app.

The route is the capability

The service built a TUN interface with a private address and a default route. In simplified form, the behavior looks like this: 

VpnService.Builder()
    .addAddress("<tun-address>", 32)
    .addRoute("0.0.0.0", 0)        // default route: all IPv4 egress
    .addDnsServer("<dns-resolver>")
    .establish()

On a real device, the addresses are assigned by the VPN implementation. The important detail is the default route: it pulls traffic from other apps into the VPN process. The app can then forward, inspect, modify, or drop that traffic. That is the same mechanism a legitimate security tool uses — and the same mechanism an attacker can abuse.

The VPN is not a remote server by default. It is a local interface. The malicious app can run a local proxy, forward traffic to its own infrastructure, or simply observe what passes through. The user sees a VPN key in the status bar and may assume they are protected.

The second stage

The initial APK did not contain the full payload. A receiver contacted rotating infrastructure, downloaded an encrypted blob, wrote it to the app’s private cache, decrypted it with a bundled key, and loaded it with DexClassLoader. This keeps the installed package smaller, makes store review harder, and lets the operator change behavior after installation. 

// Behavioral sketch — values and class names removed
download(<encrypted-module>)
  → write(cacheDir/<random>)
  → decrypt(<bundled-key>)
  → DexClassLoader.loadClass(<entry-point>)

Dynamic loading is not inherently malicious — many apps use it for feature modules. In this context, it explained why the visible APK looked incomplete. The real capability arrived after installation.

What it can see — and what it cannot

It is tempting to describe a rogue VPN as “reading every message.” That is usually inaccurate. A local VPN sees the traffic that passes through it, but modern apps use TLS. Without a trusted interception certificate, the VPN sees connection metadata: destinations, DNS queries, SNI in some cases, timing, and volume. Cleartext HTTP is fully visible. TLS content is not.

This does not make the capability harmless. The app can redirect traffic, block updates, inject content into cleartext sessions, profile behavior, and combine the network position with other permissions. It can also prompt the user to install a second payload. The accurate risk is control and follow-on access, not magical decryption.

Precision matters

Overstating what malware can do makes the report easier to dismiss. State the observed capability, the conditions required for more, and the impact that follows. That is more useful to a defender than a dramatic claim.

Detection signals that generalize

Indicators change; behavior is more stable. The following signals are useful across families:

  • An application requesting BIND_VPN_SERVICE that is not an approved VPN or security tool.
  • A VPN route covering all addresses, especially when the app is not a known enterprise VPN.
  • Dynamic DEX loading shortly after installation, particularly from a cache directory.
  • REQUEST_INSTALL_PACKAGES combined with a sideloaded distribution path.
  • DNS queries to unexpected external resolvers, or a sudden change in resolver behavior.
  • Repeated connections to newly registered or rotating domains from a non-browser app.
  • Accessibility or overlay permissions requested alongside network capabilities.

None of these is conclusive alone. Correlate them with installation source, user reports, and network behavior.

Defense: remove the position, not just the sample

Blocking one package is temporary. The durable controls are about who can obtain this position in the first place:

  • Disallow sideloading on managed devices and alert on unknown-source installs.
  • Treat VPN permission as a privileged capability; require approval and log its use.
  • Restrict REQUEST_INSTALL_PACKAGES through MDM policy where possible.
  • Monitor egress for external DNS resolvers, unusual VPN interfaces, and known-bad infrastructure.
  • Pair endpoint detections with a response playbook: remove the app, revoke sessions, rotate credentials, review second-stage activity.

The most important lesson is not about a specific malware family. It is that Android’s permission model gives users the ability to grant away a network position that most people do not understand. Security teams should treat that grant as a control point — and attackers already do.
