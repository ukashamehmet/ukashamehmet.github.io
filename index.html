How I work / 02

A test should survive contact with engineering.

Findings are not the deliverable. A change that holds is. My process is built to make the risky path obvious, the evidence reproducible, and the fix testable by the people who own the system.

“A finding isn’t closed when the report is sent. It’s closed when the fix survives a retest.” Working principle
  1. 01

    Scope without surprises

    Threat model, rules of engagement, test accounts, escalation path, and success criteria. Production is treated as production from the first request.

  2. 02

    Map what the system trusts

    Recon, role matrices, data flows, API contracts, and configuration review. I look for the assumptions between components, not just missing patches.

  3. 03

    Prove the smallest real path

    Manual exploitation with the minimum access needed to demonstrate impact. No bulk data collection, no unnecessary persistence, no theatre.

  4. 04

    Translate risk into repair

    Business impact, CVSS, affected component, exact remediation, owner, and priority. A finding an engineer cannot action is an unfinished finding.

  5. 05

    Retest, then close

    Replay the original path, test adjacent routes, review the fix, and issue a closure memo. The client gets evidence, not a promise.
