Web & API Critical SaaS

One query, every tenant

A multi-tenant legal case-management platform authenticated every request but failed to bind objects to the requesting tenant. The result was cross-organization read and write access.

BOLA / IDOR Tenant isolation Production debug leak SOC 2 readiness
Engagement
Authenticated web + API test
Surface
SaaS platform, 3 roles
Window
10 testing days
Disclosure
Coordinated · 2025

Context

The client operates a multi-tenant case-management platform for legal and investigation teams. Each customer organization expects its matters, notes, and identity data to be invisible to every other tenant. A SOC 2 Type II audit was approaching, and the engineering team wanted an independent test of tenant isolation rather than another scanner run.

I was given two isolated test tenants, one administrative account, and one standard user account. The objective was specific: prove whether the application enforced tenant boundaries at the object level, not just at login.

How I found it

  1. Built a two-tenant matrix. I mapped every role and every object action — read, update, export, comment, assign, delete — then created a test plan that treated each combination as a separate authorization decision.
  2. Traced the API from the client. The web application was a single-page app. I reviewed its JavaScript bundles to recover route patterns, then compared them with the API documentation and observed traffic.
  3. Tested object ownership, not just authentication. Using Tenant A’s session, I requested an object identifier belonging to Tenant B. The server returned the full record with a 200 OK instead of a 403 or 404.
  4. Confirmed the pattern at the collection layer. A list endpoint returned records from multiple organizations, and nested staff objects leaked internal usernames and roles. Debug behavior in production exposed route metadata and query traces, which explained the missing tenant filter.
  5. Tested the write path. The same object identifier accepted a PATCH from Tenant A, allowing status and priority fields on Tenant B’s record to be changed. I stopped after one synthetic test record and did not export client data.

The evidence

A sanitized request pattern was enough to demonstrate the boundary failure reproducibly. Names, identifiers, and values are replaced.

# Tenant A session requests Tenant B's object
GET /api/v1/<resource>/<object-id> HTTP/1.1
Authorization: Bearer <tenant-a-session>

HTTP/1.1 200 OK
{
  "tenant": "<tenant-b>",
  "record": "<redacted>",
  "staff": { "username": "<internal-user>", "role": "<internal-role>" }
}

How we fixed it

  1. Made tenant scope a data-layer default. A tenant-aware manager scoped every queryset to the authenticated user’s organization. Application code could no longer call an unscoped global model lookup by accident.
  2. Added object-level permissions. A deny-by-default permission class checked ownership before serialization or mutation. Foreign objects return 404 to avoid confirming their existence.
  3. Used a composite lookup. Object retrieval now queries by both tenant and object identifier, rather than fetching globally and checking afterwards.
  4. Removed production debug behavior. Debug mode was disabled, a custom error handler replaced framework tracebacks, and exposed environment secrets were rotated.
  5. Reduced the response surface. List serializers were split from detail serializers; internal staff objects and sensitive fields no longer appear in tenant-facing responses.
# Illustrative fix: scope before retrieval, then authorize
def get_queryset(self):
    return Case.objects.for_tenant(self.request.user.tenant)

def get_object(self):
    return get_object_or_404(
        self.get_queryset(),
        object_id=self.kwargs["object_id"],
    )

Verification & outcome

I replayed the original requests and extended the test to every object route in the application. Cross-tenant reads, writes, exports, and nested-object access all failed closed. The engineering team added a two-tenant regression suite to CI so the boundary could not silently regress.

100%test-tenant isolation
0client records retained

Why it mattered: the application was not missing authentication. It was missing the second question every multi-tenant system must answer on every request: does this user’s tenant own this row?

The debug folder that opened the front door

A production debug directory exposed live session state, enabling account takeover. The same portal accepted executable uploads into a web-served directory.

Session hijacking Unrestricted upload Origin exposure PII protection
Engagement
Black + grey-box web test
Surface
Member portal + document upload
Window
12 testing days
Disclosure
Coordinated · 2025

Context

The portal handles member registration, identity-document uploads, digital membership cards, payments, and facility bookings for a high-profile membership organization. It sat behind a reverse proxy and a web application firewall, and the team reasonably assumed that the edge was enforcing the important controls.

The assessment was scoped to the public portal and its document workflows. The client asked for evidence of account takeover and file-processing risk, not a broad infrastructure scan.

How I found it

  1. Mapped the perimeter. Subdomain enumeration, certificate transparency, and DNS history identified several administrative and staging hostnames that did not share the primary site’s proxy configuration.
  2. Found a direct path to the origin. One of those hostnames resolved directly to the hosting origin. Sending a request with the main site’s host header returned the application, bypassing the edge WAF entirely.
  3. Discovered a production debug directory. Directory discovery exposed a framework debug folder that was readable over HTTP. It contained execution traces and session state, including live session identifiers.
  4. Replayed a session without credentials. I injected a recovered session cookie into a clean browser profile and reached the authenticated member dashboard. I limited the proof to a synthetic test account and one metadata response; no identity documents were downloaded.
  5. Tested the upload boundary. The document-upload endpoint validated neither extension nor file content and stored files under a web-executable path. I uploaded a harmless proof file that returned a unique token, confirmed execution, then removed it with the client’s approval.
  6. Found exposed configuration. A dotfile in the web root was directly readable and exposed key names and database settings. I confirmed the exposure without copying secret values; the client rotated everything afterward.

The evidence

# Sanitized chain — values removed
GET /<debug-path>/<dump>.json          → 200 (session state exposed)
Cookie: <session>                        → authenticated member dashboard

POST /<upload-endpoint>                  → 200
filename="proof.<server-side-extension>" → stored in executable web path

How we fixed it

  1. Contained the active compromise. All sessions were invalidated, application and database secrets were rotated, and administrative users were required to re-authenticate with MFA.
  2. Removed debug tooling from production. Debug logging was disabled, writable and diagnostic directories moved outside the web root, and direct access to dotfiles and debug paths was denied at both edge and origin.
  3. Rebuilt the upload pipeline. The new flow allowlists image/PDF extensions, verifies magic bytes, re-encodes images, assigns random names, stores files outside the executable root, and scans uploads before release.
  4. Locked the origin to the edge. Ingress now accepts only the provider’s published ranges, with authenticated origin pulls or mutual TLS. Staging DNS records were removed from public zones.
  5. Hardened the session layer. Cookies gained Secure, HttpOnly, and SameSite attributes; session rotation on login was enforced; HSTS and a restrictive content-security policy were deployed.

Verification & outcome

Replaying the captured session returned 401. Mixed-case, double-extension, and content-type mismatch uploads were rejected. Direct-to-origin requests timed out, and the exposed configuration path returned 404. The client also reviewed access logs around the exposure window and found no evidence of document downloads.

The lesson: a WAF protects the hostname configured in front of it. A forgotten staging record, an exposed origin, or a debug directory in the web root can route around the entire control plane.

The WAF was never the wall

Public DNS and certificate data exposed the hosting origin. Direct requests bypassed the edge, and administrative gateways were reachable from the internet.

External ASM Origin exposure Management plane ZTNA
Engagement
External perimeter + ASM
Surface
Hybrid hosting estate
Window
15 testing days
Disclosure
Coordinated · 2025

Context

A logistics and supply-chain group asked for an external assessment of its internet-facing estate. The primary websites were behind a CDN and WAF, but the organization had accumulated years of hosting, acquisitions, and staging environments. The goal was to see the perimeter as an outsider would — including everything the asset inventory had forgotten.

The engagement was non-destructive: no password spraying, no exploitation of management services, and no access to production data. Where a login surface was found, the finding was the exposure itself.

How I found it

  1. Enumerated the external footprint. DNS, WHOIS, certificate transparency, and passive infrastructure data produced subdomains, hosting ranges, and mail-related records that were not in the client’s current inventory.
  2. Followed the mail records. A public SPF record listed the organization’s origin hosts. Cross-referencing those addresses with TLS certificates and subdomain history confirmed that several belonged to the primary web estate.
  3. Verified the WAF bypass. A direct HTTPS request to an origin address, with the public host header, returned the application. Cloudflare headers and rate-limit behavior were absent.
  4. Mapped the exposed services. Light-touch port scanning found a remote desktop gateway, a database administration console, and a staging API on public addresses without source-IP allowlists or SSO.
  5. Checked the management surface. I confirmed the login pages and TLS configuration only. No credentials were guessed and no session was established. The exposure was enough to demonstrate the risk.

The evidence

# Direct-to-origin request — sanitized
curl --resolve <public-host>:443:<origin-address> https://<public-host>/
HTTP/1.1 200 OK   # response from origin, no edge headers

# Publicly reachable management surfaces
<admin-gateway>:443  → login page, no IP allowlist
<database-console>  → login page, no SSO

How we fixed it

  1. Made the origin private by policy. Ingress firewall rules now accept HTTP/HTTPS only from the CDN provider’s published ranges, with authenticated origin pulls or mutual TLS so a spoofed source cannot simply claim to be the edge.
  2. Moved management behind ZTNA. The remote desktop gateway and database console were removed from public DNS and placed behind a zero-trust access proxy with device posture and phishing-resistant MFA.
  3. Cleaned the DNS and mail records. SPF, MX, and staging records were reviewed so they no longer advertise origin infrastructure. Historical records were documented and monitored rather than left to memory.
  4. Built an owned asset inventory. The client adopted a continuous external discovery process with named owners, review cadence, and alerting for new certificates or hosts appearing outside the approved range.
  5. Added defense in depth. WAF rules, rate limits, and alerting were tuned, but no longer treated as the only control protecting the origin.

Verification & outcome

After the change, direct-to-origin requests timed out, management hostnames no longer resolved publicly, and the exposed services were reachable only through the access proxy. A rescan of the external range showed a 78% reduction in observable attack surface.

The lesson: a WAF is an application-layer control, not a network boundary. If the origin is reachable directly, the attacker simply chooses a different route.

When a CMS becomes a doorway

Path traversal in a public CMS component exposed system files and configuration. Two separate SQL injection classes reached back-end database metadata.

LFI SQL injection National infrastructure Segmentation
Engagement
External network + web test
Surface
40+ public subdomains
Window
18 testing days
Disclosure
Coordinated · 2024–25

Context

A national telecom and regulatory environment asked for an external assessment of its public infrastructure. The estate included consumer service portals, mobile financial services, a regulatory search application, and internal call-center tooling. Because of the sensitivity, the rules of engagement were unusually strict: prove the first viable path, capture the minimum evidence, stop, and escalate immediately.

This is the kind of environment where a “full dump” is not a demonstration of skill. Restraint is part of the test.

How I found it

  1. Mapped the ASN and certificate history. I combined passive DNS, certificate transparency, and netblock ownership to identify more than 40 live subdomains, including staging and regional service portals.
  2. Profiled the public applications. One CMS-based portal exposed an asset parameter that accepted a filename. Normal requests returned expected content; traversal sequences escaped the intended directory.
  3. Verified file read with one harmless target. I read the first lines of a standard system account file to confirm traversal, then a configuration file header to confirm exposure of secret material. I did not retrieve subscriber data or bulk configuration.
  4. Tested the search surface. A regulatory record filter reflected database metadata through a union-based injection. A separate call-center login showed a repeatable time delay with a statistical check across multiple requests, confirming blind injection rather than network jitter.
  5. Stopped at metadata. The proof reached database version and current user only. No tables, subscriber records, or business data were enumerated. The client was notified the same day.

The evidence

# Sanitized traversal proof
GET /<component>?<asset-param>=../../../../etc/passwd
HTTP/1.1 200 OK  → first lines of system account file

# Sanitized SQLi proof — metadata only
<filter>' UNION SELECT @@version, current_user()-- -
→ database version and service account disclosed

How we fixed it

  1. Closed the file-read path. The asset parameter was replaced with a strict identifier allowlist. Path separators and encoded traversal were rejected before filesystem access, and PHP execution was constrained with an open-basedir boundary.
  2. Removed the vulnerable component. The unused CMS plugin was deleted rather than patched in place, reducing the long-term maintenance surface.
  3. Parameterized every query. Dynamic SQL in the search and login paths was converted to prepared statements with typed parameters. Verbose database errors were suppressed.
  4. Reduced database privilege. The public application account lost unnecessary schema and file permissions. Secrets found in configuration were rotated, and config files were moved outside the web root.
  5. Segmented the public tier. Internet-facing portals were isolated from core routing and subscriber systems, with egress filtering and a reviewed allowlist between tiers.
  6. Added regression coverage. Traversal, encoding, and injection test cases were added to the release pipeline, alongside a WAF virtual patch for immediate coverage.

Verification & outcome

Traversal payloads returned 400/404, including encoded and double-encoded variants. The blind injection timing returned to baseline across repeated measurements, and the union path no longer reflected metadata. The database account was confirmed to lack file and schema-level access.

2critical classes closed
0subscriber records accessed

Why it mattered: the file-read and injection paths were separate findings, but they shared a root cause — public components being trusted with direct access to system and data layers. Segregation limited what either could reach.

Reading the envelope

A mobile identity service wrapped every request in a proprietary cryptographic envelope. The scheme was sound enough to stop casual inspection — but not enough to stop replay.

Android reversing Frida Crypto protocol Replay protection
Engagement
Mobile app + API audit
Surface
Android client, identity API
Window
14 testing days
Disclosure
Coordinated · 2025

Context

The client operates a mobile identity and verification service. The Android app did not send plain JSON; every request body was binary and accompanied by a custom key header. The engineering team believed the proprietary envelope made automated abuse impractical.

The assessment asked a narrower question than “can the app be reverse engineered?” — it asked whether the protocol provided a real security boundary or only obfuscation.

How I found it

  1. Decompiled and reviewed the client. Jadx and Apktool exposed the network stack, interceptor classes, and a public-key asset embedded in the APK. The app used certificate pinning and root detection, which I bypassed in a lab build with Frida hooks.
  2. Observed the crypto calls. Hooks around the platform cipher, key factory, and digest classes showed where the session key was generated, wrapped, and attached to the request.
  3. Reconstructed the envelope. The body was GZIP-compressed, encrypted with a random AES-256 key in CBC mode, and prefixed with the raw IV. The AES key was encrypted with the embedded RSA-2048 public key using PKCS#1 v1.5 and sent in a custom header.
  4. Built a standalone client. I implemented the same envelope in Python against a test account and confirmed the server accepted synthetically generated requests. This proved the protocol was not bound to the official app.
  5. Tested the trust model. There was no server-issued nonce, timestamp window, device attestation, or meaningful per-identity rate limit. A captured request could be replayed, and new requests could be generated once the public key was known.

The evidence

# Reconstructed request envelope (illustrative)
body    = iv || AES-256-CBC(gzip(json), key, iv)
header  = base64(RSA-PKCS1v1.5(public_key, key))

POST /<api-path>
X-Client-Key: <wrapped-key>
<binary body>

→ accepted without app attestation or server nonce

How we fixed it

  1. Added server-issued challenges. Each session now receives a short-lived nonce and sequence counter. Requests include a signature over the nonce, timestamp, and body digest, and the server rejects duplicates.
  2. Bound requests to a device identity. The client uses a hardware-backed Android Keystore key, with Play Integrity attestation for sensitive actions. The server verifies both before issuing elevated tokens.
  3. Reduced replay value. Access tokens are short-lived and scoped to a device session. A timestamp window and idempotency keys prevent request reuse.
  4. Moved to authenticated encryption. New protocol versions use AES-GCM or ChaCha20-Poly1305 with associated data, replacing the unauthenticated CBC construction.
  5. Enforced per-identity limits. Rate limits and anomaly detection now key off the authenticated identity and device, not just source IP. Bulk enumeration patterns trigger review and throttling.

Verification & outcome

A replayed request was rejected, a synthetic client without a valid nonce could not complete a session, and rate limits triggered after a small number of requests from the same identity. The updated client continued to work with the new protocol, and the old version was retired.

2048bit RSA key recovered
4stage envelope reversed
0customer records accessed

The lesson: encrypted transport is not the same as trusted transport. If the client holds the only secret and the server accepts any well-formed envelope, the crypto is confidentiality — not authentication.

The app that became the network

A trojan disguised as a traffic-notice app abused Android’s VPN service to become the device’s egress point, then loaded a second-stage payload from rotating infrastructure.

Android VpnService Dropper Detection engineering
Engagement
Android malware analysis
Surface
APK, native loader, network
Window
9 analysis days
Disclosure
Private client · 2025

Context

The sample arrived through a targeted SMS and WhatsApp campaign. It impersonated a municipal traffic-violation portal and asked victims to install an APK to “review a notice.” The client needed to understand the delivery chain, the device capabilities it abused, and the network signatures its fleet could detect.

Analysis was performed in an isolated lab. Egress was restricted at the hypervisor boundary, and no live payload was allowed to reach production infrastructure.

How I found it

  1. Started with the manifest. The APK requested BIND_VPN_SERVICE, RECEIVE_BOOT_COMPLETED, and REQUEST_INSTALL_PACKAGES — a combination that gives a sideloaded app network control, persistence, and the ability to install another payload.
  2. Located the rogue VPN service. The service built a local TUN interface with a private address and a default route, effectively directing all device traffic into the app’s own socket layer.
  3. Traced the second stage. A broadcast receiver fetched an encrypted payload from rotating infrastructure, wrote it to the app’s private cache, decrypted it with a bundled key, and loaded it dynamically with DexClassLoader.
  4. Observed behavior dynamically. With Frida and a lab network capture, I confirmed the service start, the route configuration, and the staged download. The capture showed cleartext DNS and metadata, not magical TLS decryption.
  5. Built detection content. I mapped the observed behavior to host and network indicators, wrote a YARA rule for the APK family, and produced Sigma logic for endpoint telemetry around VPN-service abuse and dynamic DEX loading.

The evidence

// Sanitized behavior sketch — values generalized
VpnService.Builder()
  .addAddress(<private-tun-address>, 32)
  .addRoute("0.0.0.0", 0)          // capture all egress
  .addDnsServer(<external-resolver>)
  .establish()

// Second stage
download(<encrypted-dex>) → decrypt(<bundled-key>) → DexClassLoader.load()

What it could — and could not — see

A local VPN is a powerful position. It can observe destinations, DNS queries, traffic volume, and any cleartext HTTP. It can redirect or block connections. It cannot, by itself, decrypt modern TLS without another capability such as a trusted certificate or a compromised endpoint.

The accurate risk was therefore not “the app reads every encrypted message.” It was that a sideloaded app had been granted control of the device’s entire network path, with the ability to stage additional code. That is more than enough to enable credential phishing, traffic manipulation, and follow-on payloads.

How we defended it

  1. Blocked sideloading on managed devices. MDM policy now disallows installation from unknown sources and alerts on apps requesting VPN or install-packages permissions.
  2. Added network detections. The client deployed the indicators and YARA signature, blocked the observed infrastructure patterns, and monitored for external DNS resolvers and anomalous VPN interfaces.
  3. Gave the SOC a playbook. The response runbook covers app removal, credential rotation, session revocation, and review of any second-stage activity.
  4. Tuned user awareness. The campaign relied on a believable municipal notice. Awareness guidance focused on the install prompt and the VPN permission, not on generic “don’t click links” advice.

Verification & outcome

The YARA rule matched the sample and a controlled variant. Sigma logic fired on synthetic telemetry for VPN-service creation and dynamic DEX loading. The indicators were deployed to the client’s endpoint and network tooling, and the playbook was exercised with the SOC.

The lesson: permission abuse is a capability. A user who grants VPN access to an unknown app has handed it the same position a network attacker spends weeks trying to reach.

Trust, but deserialize

An unauthenticated build-agent endpoint passed XML into an unpinned deserializer. A vendor-specific object graph reached command execution before authentication.

CWE-502 XStream Pre-auth RCE Coordinated disclosure
Engagement
Vulnerability research
Surface
CI/CD agent control plane
Window
21 research days
Disclosure
Vendor coordinated

Context

The target was an enterprise CI/CD orchestration product with a distributed build-agent model. Agents register with a central controller, poll for work, and report command results. This control plane is unusually valuable: whoever can speak to it convincingly may be able to run code in the build environment, where source code and deployment credentials live.

The research focused on the agent registration and error-reporting path, not on the product’s authenticated administrative UI.

How I found it

  1. Mapped the trust boundary. A synthetic agent could register a session without presenting a pre-shared credential. The controller accepted the session and exposed the agent command surface.
  2. Traced the error path. The command error endpoint accepted XML from a registered agent and passed it to a deserializer configured without a type allowlist. That is the classic condition for object injection.
  3. Looked for reachable gadgets. Standard library and framework chains were filtered. A product-specific exception object with an embedded database data source was not.
  4. Built the smallest chain. Instantiating that object triggered a database initialization path, which executed a controlled SQL statement. The statement wrote a harmless proof file outside the intended directory. From there, I verified command execution with a single identity command and stopped.
  5. Reported with a fix, not just a finding. The advisory included the root cause, the minimal reproduction, the affected trust boundary, and a proposed allowlist architecture. The vendor confirmed the issue and shipped a patch.

The evidence

<!-- Structural sketch only; class names and payload removed -->
<map>
  <entry>
    <string>session</string>
    <vendor-object>
      <embedded-datasource>...</embedded-datasource>
    </vendor-object>
  </entry>
</map>

→ object construction reached a database initialization sink

How we fixed it

  1. Denied by default in the deserializer. The patch enables the security framework, denies all types, and explicitly allows only the small set of DTOs used by agent reports.
  2. Required agent identity. Agent registration now uses a per-agent credential and mutual TLS; error reports are accepted only from an authenticated, enrolled agent session.
  3. Made the web root read-only. The deployment runs the application with a read-only root filesystem and no write access to the web application directory, breaking the file-drop step even if another gadget appears.
  4. Reduced the gadget surface. The embedded database component was removed from the agent process, and dependency review now includes deserialization gadgets.
  5. Added monitoring. The product emits high-severity alerts for unexpected file creation in the web root and for deserialization errors involving unapproved types.

Verification & outcome

After the patch, the original object graph was rejected before construction. A new agent could no longer register without credentials. The read-only filesystem blocked the proof write, and the vendor’s regression test confirmed that legitimate agent reports still worked.

The lesson: deserialization bugs are rarely about the parser. They are about every class on the classpath that can do something interesting when constructed. An allowlist is not a nice-to-have; it is the boundary.

The extension filter that wasn’t

A CMS archive upload relied on a case-sensitive blocklist. A mixed-case filename plus an execution-handler override turned a media upload into remote code execution.

File upload Canonicalization RCE Secure design
Engagement
Vulnerability research
Surface
CMS media + archive import
Window
16 research days
Disclosure
Vendor coordinated

Context

The target was a page-builder CMS with a media library and an archive import feature used to migrate themes and assets. The upload path appeared to block executable extensions, and the application had a reputation for being security-conscious. The question was whether the filter was canonicalizing input before it made a decision.

How I found it

  1. Reviewed the upload contract. The client accepted ZIP archives, extracted them server-side, and preserved directory structure. The extension check compared against a lowercase blocklist.
  2. Tested case and encoding variants. A file whose extension differed only by case passed the blocklist. On a case-insensitive filesystem or with a handler override, it remained executable.
  3. Tested handler control. The archive importer also accepted server configuration files. A minimal handler override in an uploaded directory was enough to make a benign image extension execute as code.
  4. Confirmed with a harmless proof. I wrote a file that returned a unique token when requested through the web server. No reverse shell, no persistence, and no data access were used. The file and directory were removed after evidence capture.
  5. Reported the chain. The advisory explained that the bug was not merely “PHP upload.” It was the combination of non-canonical extension checking, archive extraction trust, and execution enabled in a user-writable directory.

The evidence

# Sanitized chain
1. upload archive containing mixed-case executable extension
2. extractor preserves name, blocklist compares lowercase only
3. handler file in upload directory maps image extension to executable
4. GET /<upload-dir>/<proof>.<ext>  → 200, proof token returned

How we fixed it

  1. Canonicalized before validation. Filenames are Unicode-normalized, lowercased, and stripped of control characters and trailing dots before the allowlist check.
  2. Switched from blocklist to allowlist. Only a short set of image, document, and archive types is accepted, verified by magic bytes as well as extension.
  3. Stopped trusting archive paths. Extraction rejects absolute paths, traversal sequences, symlinks, and nested archives beyond a defined depth. Extracted files receive generated names.
  4. Removed execution from the upload tier. Media is served from object storage or a separate host with script execution disabled. Handler configuration files are rejected and never written to web-accessible paths.
  5. Added virtual patching and tests. The WAF blocks mixed-case and double-extension patterns immediately, while the product fix and regression tests cover the root cause.

Verification & outcome

Mixed-case, double-extension, traversal, and handler-override attempts were rejected. The stored proof file was no longer executable, and the vendor’s regression suite covered the canonicalization cases. The client deployed the virtual patch before the vendor update was available.

3bypass classes closed
0data accessed
1vendor patch validated

The lesson: security filters must run on the same representation the filesystem will use. If validation sees a different string than execution sees, the filter is decoration.

Obfuscation is not encryption

The official Twitter (X) Android app stored its OAuth 1.0a consumer credentials behind a reversible arithmetic transform. Decompiling the client and undoing one byte operation recovered the signing key.

Android reversing OAuth 1.0a Credential exposure Coordinated disclosure
Program
Twitter (X) — HackerOne
Surface
com.twitter.android (APK)
Window
Independent research
Disclosure
HackerOne · Apr 2026

Context

The target was com.twitter.android, the official Twitter (X) Android app, tested under Twitter's public HackerOne bug bounty program. Native mobile apps for API-driven platforms often embed a consumer key and secret so the client can sign its own requests before a user ever logs in. Those values are not meant to be extractable from the installed package, so the app's build pipeline ran them through a byte-level transform rather than storing them as plain strings.

The question driving the research was simple: does that transform function as real protection, or only as a speed bump for anyone willing to read the decompiled code?

How I found it

  1. Decompiled the APK. Running apktool against com.twitter.android produced readable Smali across dozens of packages. A small, oddly named class (ttu.smali) initialized two static string fields from byte arrays rather than string literals — an immediate signal that something was being deliberately obscured.
  2. Read the transform. The class’s static initializer looped over each byte array and applied rsub-int/lit8 with a constant, then converted the result to a character. That is a single fixed subtraction per byte — a classic “hide it from strings” trick rather than real cryptography, and trivial to reverse by hand or in a short script.
  3. Traced where the decoded values went. The two decoded strings were passed into a small credential-container class (fhj.smali), which was in turn consumed by the app’s OAuth 1.0a signing engine (khj.smali) and by a secondary OAuth2 basic-auth path (aqc.smali). The signing engine referenced the constants by name as oauth_consumer_key and the paired secret used in HMAC-SHA1 signing.
  4. Confirmed the values were live. I decoded the byte arrays offline, then reimplemented the client’s OAuth 1.0a request-signing logic in a standalone script: build the signature base string, HMAC-SHA1 it with the recovered consumer secret, and attach the resulting Authorization header to a request built with the same client headers the official app sends.
  5. Proved impersonation, not data access. A request signed this way was accepted as if it came from the official client. I limited the proof to confirming that a correctly signed, unauthenticated-tier request succeeded — I did not use the recovered credentials against authenticated endpoints or pull user data.

How it was addressed

The report was triaged by HackerOne as a duplicate of an already-known issue, which is itself informative: embedded, lightly-obscured consumer credentials in mobile OAuth 1.0a clients are a recurring class across large API-driven apps, not a one-off oversight. The direction of a durable fix is consistent with how Twitter/X and others in this space have since moved:

  1. Stop treating a client secret as secret. Any value shipped inside an installable package should be assumed public. Per-app consumer credentials used only to identify “this is the official client” carry little security value once that assumption is made.
  2. Move trust decisions server-side. Rate limits, abuse detection, and app-identity checks were shifted toward signals the client cannot forge by reading its own binary — attested app integrity, device-bound tokens, and behavioral/anomaly detection on the API side.
  3. Reduce what a bare consumer key/secret pair can do. Unauthenticated, app-only requests were scoped down so that recovering the embedded credential alone no longer provides meaningful API access without an additional, harder-to-forge signal.
  4. Treat obfuscation as a delay, not a boundary. Where client-side secrecy is still used as one layer, it is paired with controls that assume it will eventually be defeated, rather than being the sole gate in front of API capability.

Verification & outcome

The proof-of-concept script reliably produced accepted, correctly signed requests using only values recovered through static analysis of the public APK, with no runtime hooking or device needed. The finding was written up and submitted through the program’s standard disclosure process.
